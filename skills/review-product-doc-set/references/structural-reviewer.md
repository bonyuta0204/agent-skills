# Structural Reviewer — 文書構造レビュー

## 役割

文書セット全体を **構造** の観点でレビューする。
各文書が本来の責務に収まっているか、重複や整合性の問題がないかを見る。

## レビュー観点

### 1. 責務分離

各文書が担うべき責務は以下のとおり。

| 層 | 文書 | 責務 |
|---|------|------|
| WHY | 要件定義書 | なぜ作るか — 背景・課題・ユースケース・スコープ |
| WHAT | 仕様書 | 処理ロジック・ビジネスルール・データ制約・API 契約 |
| INTERACT | 画面仕様書 | 操作したら何が起きるか — イベント→アクション→遷移 |
| UI | Figma | 見た目・配置・文言・状態バリエーション |
| COMMON | 共通仕様書 | プロダクト横断の入力制御・バリデーション・表示ルール |

確認すること:

- 要件定義書が処理手順や UI 詳細に踏み込んでいないか
- 仕様書がボタン文言・レイアウト・画面遷移まで抱え込んでいないか
- 画面項目定義書が条件分岐・内部処理ロジックまで持っていないか
- Figma に業務ルールや条件分岐が押し込まれていないか
- 共通仕様書に集約すべき横断ルールが個別文書に散っていないか

### 2. 重複

以下のパターンを洗い出す。

- 同じボタンやモーダルの挙動が仕様書と画面項目定義書の両方で説明されている
- 同じバリデーションルールが複数画面で繰り返し書かれている
- 同じ文言や表示条件が Notion と Figma の両方で固定されている
- 同じ処理制約が要件定義書と仕様書の両方で詳細に語られている

重複を見つけたら「どちらを正にすべきか」まで判断する。

### 3. 重複が残る場合の整合性

完全な正規化が難しい前提で、重複が残っている場合は以下を確認する。

- 条件が一致しているか
- 文言が一致しているか
- 活性/非活性・表示/非表示の条件が一致しているか
- 遷移先やアクション結果が一致しているか
- 上限値・件数制限・入力制約が一致しているか
- 例外条件や暫定仕様が片方にしか書かれていない状態になっていないか

整合が崩れている場合は、重複の存在以上に優先して指摘する。

### 4. 参照の向き

- 要件定義書から仕様書へ降りる参照になっているか
- 仕様書から画面仕様や Figma を参照する場合、責務境界を越えすぎていないか
- 画面項目定義書が仕様書の代わりに業務ルールの置き場になっていないか
- 共通仕様書への参照で済む内容を毎回個別ページへ埋め込んでいないか

### 5. 将来の分解方針への適合

現状の文書をそのまま正とせず、`画面仕様書 + Figma + 共通仕様書` への分解を前提に評価する。

- 操作起点の挙動は画面仕様書に切り出せる構造か
- 見た目や文言は Figma に寄せられるか
- 共通ルールは共通仕様書に集約できるか
- 仕様書に残すべき処理ルールと外へ出すべき UI 情報が混ざっていないか

## 出力形式

`comment-format.md` の型に従い、以下の分類でコメント案を返す。

- `MUST`: 責務逸脱、明確な矛盾、更新事故につながる重複
- `SHOULD`: 整理不足、共通化不足、将来の分解を妨げる構造
- `QUESTION`: 意図確認が必要な箇所
