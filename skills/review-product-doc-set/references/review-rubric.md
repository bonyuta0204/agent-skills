# Review Rubric

この reference は、要件定義書・仕様書・画面項目定義書を文書セットとしてレビューするときの判定軸です。

## 1. 各文書の責務

### 要件定義書で見ること

- 背景、課題、ユースケース、スコープが書かれているか
- なぜこの機能が必要かが読み取れるか
- 処理手順や UI 詳細に降りすぎていないか

### 仕様書で見ること

- 処理ロジック、ビジネスルール、データ制約、API 契約に集中しているか
- ボタン文言、見た目、細かな画面レイアウト、画面遷移まで抱え込んでいないか
- 画面ごとの操作イベントを大量に説明していないか

### 画面項目定義書で見ること

- UI 要素の定義に閉じているか
- 条件分岐、遷移、内部処理ロジックまで抱えていないか
- 現行フォーマット上やむを得ず操作情報を書いている場合でも、画面仕様書に切り出せる構造になっているか

### Figma で見ること

- 見た目、配置、文言、状態バリエーションの正になっているか
- 逆に、条件分岐や業務ルールまで Figma に押し込んでいないか

### 共通仕様書で見ること

- 入力制御、バリデーション優先順位、権限制御、エラー表示、検索仕様などの横断ルールを引き受けているか
- 同じルールが複数ページに散っていないか

## 2. 重複

以下の重複を洗い出す。

- 同じボタンやモーダルについて、仕様書と画面項目定義書の両方で挙動を説明している
- 同じバリデーションルールが複数画面で繰り返し書かれている
- 同じ文言や表示条件が Notion と Figma の両方で固定されている
- 同じ処理制約が要件定義書と仕様書の両方で詳細に語られている

重複を見つけたら、それ自体を指摘するだけで終わらせず、どちらを正にすべきかも考える。

## 3. 重複が残る場合の整合性

完全に正規化できない前提もあるため、重複が残る場合は以下を必ず確認する。

- 条件が一致しているか
- 文言が一致しているか
- 活性/非活性や表示/非表示の条件が一致しているか
- 遷移先やアクション結果が一致しているか
- 上限値、件数制限、入力制約が一致しているか
- 例外条件や暫定仕様が片方にしか書かれていない状態になっていないか

整合が崩れている場合は、重複の存在以上に優先して指摘する。

## 4. 参照の向き

文書同士の参照が自然かを見る。

- 要件定義書から仕様書へ降りる参照になっているか
- 仕様書から画面仕様や Figma を参照する場合、責務境界を越えすぎていないか
- 画面項目定義書が仕様書の代わりに業務ルールの置き場になっていないか
- 共通仕様書への参照で済む内容を、毎回個別ページへ埋め込んでいないか

## 5. 将来の分解方針への適合

レビュー時は、現状の文書をそのまま正とせず、次の分解方針に照らして評価する。

- 要件定義書: なぜ作るか
- 仕様書: 処理やルールがどう動くか
- 画面仕様書: 操作したら何が起きるか
- Figma: どう見えるか
- 共通仕様書: 複数画面で共通のルール

この将来像に照らして、今の文書がその移行を妨げていないかを見る。
