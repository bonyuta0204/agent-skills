# Create Explanatory Diagram

## この skill の目的

この skill は、設計書の補足資料や要件ディスカッションで使う **図表** を作るためのものです。

対象は、かわいい挿絵や雰囲気イラストではありません。次のような、**業務資料として読める密度を持った説明図** を扱います。

- 横長 1 枚に複数パネルを並べた図
- タイトル、サブタイトル、注記、凡例を持つ図
- 箱、矢印、表、状態一覧、条件一覧を組み合わせた図
- 設計レビューで「どこが主張か」「どこが条件か」が読み取れる図

特に向いているのは次です。

- 実装責務の切り分け
- 処理フローの全体説明
- 状態更新ロジックの説明
- 可否条件や fallback 条件の整理
- before / after 比較
- 非エンジニアも含む場での認識合わせ

## 使い分け

### この skill を使うとき

- 画像として見せる説明図がほしい
- 1 枚で全体の意味、条件、例外、ポイントまで見せたい
- 文章だけだと重いが、Mermaid だけだと資料っぽさが足りない

### `create-mermaid-diagram` を使うとき

- 実装に近い構造や分岐を厳密に表したい
- 文書にそのまま埋め込める再編集可能な図がほしい
- render 検証込みで壊れない図が必要


## 進め方

### 1. 先に意味を固定する

いきなり画像を作らない。最初に次を言語化する。

- 誰に見せる資料か
- この 1 枚で何を理解してほしいか
- よくある誤解は何か
- 図の主役は何か
- 図に含める条件、例外、注記は何か

まず次の 1 文を作る。

`この説明図は「<主題>」を説明し、<誤解> を防ぐためのもの`

### 2. 図の型を選ぶ

実画像のような説明図は、だいたい次の型に分かれる。

- `comparison`
  差分更新 / 全件更新のような比較
- `pipeline`
  source -> processing -> result の流れ
- `decision-flow`
  条件分岐と最終結果
- `state-update`
  状態と、その状態を変える契機
- `architecture`
  システムや責務の配置
- `matrix`
  可否一覧、ケース一覧、条件表

1 枚に詰め込みすぎるなら、型を混ぜるのではなく 2 枚に分ける。

### 3. Diagram Brief を作る

画像生成の前に、レビュー可能な brief を Markdown で作る。

最低限、次を含める。

- タイトル
- サブタイトル
- 主メッセージ
- 読み手
- 防ぎたい誤解
- 図の型
- パネル構成
- 主役
- 脇役
- 必須ラベル
- 必須注記
- 入れる表や凡例
- NG表現
- トーン

format は次でよい。

```md
## Diagram Brief

- タイトル:
- サブタイトル:
- 主メッセージ:
- 読み手:
- 防ぎたい誤解:
- 図の型:
- パネル構成:
- 主役:
- 脇役:
- 必須ラベル:
- 必須注記:
- 表 / 凡例:
- NG表現:
- トーン:
```

### 4. レイアウトを先に決める

この skill では、見た目より先に **どの箱をどこへ置くか** を決める。

実画像のような構成にしたいときは、次を使う。

- 上部: タイトル、短い説明、ポイント帯
- 中央: 主役の図解パネル
- 左右: 入力条件、前提、責務、補足
- 下部: ケース表、凡例、注意点、まとめ

主役は中央に置き、脇役は左右か下部へ逃がす。

### 5. 画像を作る

実行環境に応じてルートを使い分ける。**imagegen が使える環境ではまずルート A を検討する**。説明図は最終的に PNG などのラスタ画像で見られることが多く、imagegen のほうが余白、配色、カード感、情報の強弱が自然に仕上がりやすい。

ただし、**情報量が多い設計図、表、責務分担図、厳密な日本語ラベルや識別子が多い図ではルート B を優先する**。imagegen は見た目を整えやすい一方で、情報密度が薄くなったり、文字が省略・変形されたりしやすい。設計書で source of truth に近い役割を持つ図は、正確なテキストと高い情報密度を優先する。

SVG (ルート B) は単なる fallback ではなく、次の場合の推奨ルートとする。imagegen が使えない、ユーザーが SVG を明示した、既存の SVG/vector 資産に合わせる必要がある、座標・文字をピクセル単位で調整する必要がある、または図の価値が装飾より情報量と正確性にある場合。どちらを選んでも、目的（業務資料として読める密度を持つ説明図）は変わらない。

#### ルート A: imagegen が使える（Codex など）

`imagegen` skill を併用し、組み込み `image_gen` を使う。プロジェクトに差し込む図なら、生成後に `$CODEX_HOME/generated_images/...` から workspace 内の所定パスへ移す。会話プレビューだけで終わらせず、設計書や資料から参照される最終 PNG を repository 内に残す。

imagegen で作る図は、主張が 1 つで、ラベルが短く、見た目の理解しやすさが重要なものに向く。日本語ラベル、ID、SQL 断片などの誤字が許されない要素が多い場合は、imagegen の結果をそのまま採用しない。短い語だけに絞って再生成する、後処理で正確なテキストを重ねる、またはルート B に切り替える。

prompt では、題材だけでなく次を必ず明示する。

- corporate slide-style explanatory diagram
- white background, blue header bars, restrained accent colors
- multiple boxed panels, arrows, small tables, legends, notes
- Japanese labels that are readable and concise
- decorative illustration より information design を優先
- exact Japanese labels only, no invented text, no decorative filler text

prompt の順序は次がよい。

1. 画像の目的
2. 全体レイアウト
3. 主役パネル
4. 補助パネル
5. 表、凡例、注記
6. 避けたい誤解
7. トーン
8. 生成してよい文字列と、生成してはいけない文字列

例えば次のように書く。

```text
設計補足資料向けの横長 1 枚の説明図。主題は「Snowflake MERGE が差分反映の主体であり、アプリは前提を整える側である」。白背景の corporate slide-style infographic とし、上部に青いタイトルバーと短いサブタイトル、中央に5ステップの主役フロー、左右に入力条件と結果、下部に小さな表、凡例、注記を置く。主役は Snowflake MERGE の実行パネルで、アプリ側は前段として脇役にする。箱、矢印、表、注記を使って整理し、情報量は多めでも読み順が明確なことを優先する。アプリ内部で一致判定しているように見える表現は避ける。業務資料として落ち着いた青、緑、オレンジ中心の配色。
```

#### ルート B: imagegen が使えない（Claude Code など）

自分で SVG を書き、PNG にレンダリングして、その PNG を画像として読み直して視覚レビューする。

手順:

1. SVG をファイルに書く（例: `diagram.svg`）。
2. `scripts/render-svg.sh <diagram.svg>` を実行して PNG を生成する。必要なら `-w <幅>` で解像度を上げる。スクリプトは出力 PNG の絶対パスを最終行に出す。
3. その PNG を画像として読み直し、視覚的にレビューする。
4. 気になる点があれば SVG を直して 2〜3 を繰り返す。

SVG を書くときの方針:

- サイズの目安は `viewBox="0 0 1920 1080"`。縦横比や解像度は文脈に応じて自由に変えてよい。細長い matrix は `1920x720`、縦長の state-update は `1200x1400` のように、主張に合わせる。
- レイアウトの固定テンプレは使わない。Diagram Brief と選んだ型（pipeline, matrix, decision-flow, etc.）から、その場でパネル位置を決める。
- 色と font はこの skill の中で閉じさせる。他 skill の design system を引き込まない。業務資料として落ち着いた 3〜4 色に絞るのが扱いやすい。
- librsvg（`rsvg-convert`）の制約に注意する。
  - `<foreignObject>` 内の HTML は描画されない。テキストは `<text>` と `<tspan>` で組む。
  - 自動折返しはされない。改行は `<tspan x=".." dy="..">` で明示する。
  - 絵文字や外部 web font は使わない。`font-family="Hiragino Sans, Hiragino Kaku Gothic ProN, Yu Gothic, Noto Sans JP, sans-serif"` を推奨する。
  - どうしても CSS flex/grid や HTML 相当の折返しが要る図は、librsvg ではなく Chrome headless での render も検討する（`chrome --headless --screenshot --window-size=W,H file.svg`）。

### 6. レビューは自己チェックと evaluator subagent に分担する

作った本人は自分の意図に引っ張られて、意味と構図の欠陥を素通りしやすい。**自己チェックは layout (見た目) の観点に絞り、意味と構図のレビューは別 subagent に委ねる**。

#### 6-1. 自己チェック: layout の観点だけ

画像を視覚的に読み直すときは、内容の正しさではなく、レイアウトが破綻していないかだけを見る。

まず縮小表示で確認する。

- 主役パネルが一目で分かるか
- 読み順が左上から右下へ自然か
- 左右・上下のバランスが崩れていないか

次に拡大表示で layout を詰める。

- ラベルが矢印や箱の bounding box を横切っていないか
- 隣接する箱同士が重なっていないか
- テキストが箱の縁を越えていないか（librsvg は自動折返しがないので tspan 改行の破綻が出やすい）
- 2〜3 語を超える注記を arrow label に置いていないか（長い注記は凡例帯や箱内テキストに逃がす）

ここでは意味の正否を判断しない。

#### 6-2. evaluator を別 subagent として起動する

意味と構図のレビューは、会話履歴を持たない一回限りの subagent に渡す。自分で兼任しない。

briefing に必ず含める。

- 画像 PNG の絶対パスと、参照用に SVG / Diagram Brief の path
- 1 文の主題、読み手、防ぎたい誤解
- 評価軸 3 つ
  - `意味ズレ`: 主体、責務、方向、対象が事実と違う
  - `構図ズレ`: 主役が弱い、読み順が悪い、情報の強弱が崩れている
  - `可読性ズレ`: 密度過多、label 被り、tspan 改行破綻
- 出力フォーマット: 総評 / 軸別指摘 / このまま出せるか判定 / 修正 top 3
- 制約: 「良い点」は書かせない、抽象語禁止、画像を確認せず捏造禁止、具体座標・パネル名で指摘させる

`意味ズレ` が返ってきたら、prompt / SVG ではなく Diagram Brief から直す。

### 7. 差し込み位置まで決める

図を作って終わりにしない。どこに置くと効くかまで決める。

最低限、次を返す。

- 最終 Diagram Brief
- 使った prompt または SVG
- 画像（PNG）
- 図の下に置く 1〜2 文の補足
- どの節の直後に置くと効くか

補足文では、図で省略した主語や前提を固定する。

## 運用ルール

- この図を source of truth にしない
- 1 枚 1 主張を守る
- 主役と脇役の強弱を必ず決める
- 装飾より情報設計を優先する
- 「それっぽい挿絵」ではなく、「レビューで読める説明図」を目指す

## 出力

返却は原則として次の順で行う。

1. 1 文の主題定義
2. Diagram Brief
3. ルート A では画像生成 prompt、ルート B では SVG と render コマンド
4. 生成画像（PNG）
5. 差し込み位置と補足文
