# Comment Format

レビューコメント案は、次の型で書く。

## 基本形

1. どの箇所が問題かを短く述べる
2. なぜ問題かを説明する
3. どの文書へ寄せると整理しやすいかを説明する

## 書き方の方針

- `UI` や `COMMON` のような記号だけで終わらせず、日本語で説明する
- 「移し先」というラベルだけを置くのではなく、なぜそこへ寄せるべきかまで書く
- 現状の重複がやむを得ない場合でも、整合性が崩れていれば先に指摘する
- 読み手が次に直すべきことをすぐ判断できる粒度で書く

## 例

### MUST

- 仕様書側でボタン文言やモーダル文言まで固定しており、Figma と二重管理になっています。文言変更のたびに仕様書と Figma の両方を直す必要があるため、更新漏れが起きやすい状態です。仕様書では処理ルールに絞り、文言と見た目は Figma を正にした方が整理しやすいです。

- 同じ保存ボタンの非活性条件が仕様書と画面項目定義書で食い違っています。重複を残す前提でも条件が一致していないと、実装・QA・デザインの解釈が分かれます。少なくとも正とする文書を明確にし、他方は参照に寄せる必要があります。

### SHOULD

- 画面ごとに同じ入力制御ルールが繰り返し書かれており、今後も整合を保つコストが高いです。個別画面に閉じないルールは共通仕様書にまとめ、各画面では必要な箇所だけ参照する構成に寄せたいです。

- 画面項目定義書がクリック時の条件分岐や遷移まで詳しく持っており、操作仕様の置き場も兼ねています。将来的に画面仕様書へ分解していく前提なら、操作起点の挙動は画面仕様として独立させ、画面項目定義書は UI 要素定義に寄せた方が見通しが良くなります。

### QUESTION

- この非活性条件は画面固有のルールとして残したいのか、それとも複数画面で共通の表示制御基準として扱いたいのかが読み取りづらいです。後者であれば、個別ページに持たせるより共通仕様書にまとめた方が整合性を維持しやすいです。
