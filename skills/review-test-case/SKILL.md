# Review Test Case

このスキルは **観点駆動（viewpoint-driven）** の設計思想に基づいてテストケースをレビューする。

中心となる問いは「何を操作するか？」ではなく、**「どの仕様を確認しているか？」** である。良いテストケースは、まず仕様の主張から出発し、その主張が真となる条件を導き、それを観測するために最小限の操作と期待値を選ぶ。

## 言語ポリシー

- **入出力ともに日本語で行う。** ユーザーへの説明・質問・レビューサマリ、および成果物（修正案・インライン提案・例示テーブル）すべてを日本語で記述する。
- 専門用語（観点 / パターン / 手順 / 期待値）はそのまま使用する。
- ユーザーが他言語でメッセージを送ってきた場合でも、こちらの応答は日本語を維持する。

## 基本モデル

テストケースの 1 行は、次の 3 つの列（またはセクション）に明確に分解できなければならない。

| 列 | その内容 | その内容ではないもの |
| --- | --- | --- |
| 観点 | 確認したい仕様の主張 | UI 操作、ボタンの活性状態、画面チェック |
| パターン | 観点を確認するために変化させる条件 | すべての入力の全組合せ（クロス積） |
| 手順 / 期待値 | 具体的な操作と観測可能な結果 | 観点を言い換えただけの文 |

いずれかが別の列に潰れて混ざっている場合、そのテストケースは設計が甘い状態である。

## レビューチェックリスト

チェックは上から順に適用する。MUST 違反を見つけた場合は、先に書き換えを依頼してから次のチェックへ進む。

### 1. 観点レイヤ — MUST

- [ ] 各観点は **仕様の主張** を述べているか（UI 操作の記述になっていないか）。
  - 悪い例: 「グループ化方法を追加できること」
  - 良い例: 「グループ化動作の追加上限が正しく制御されること」
- [ ] 観点は「どの仕様を確認するか？」に答えているか。「何をクリックするか？」に答えていないか。
- [ ] ボタンの活性/非活性、表示有無、トースト表示などは観点ではなく **期待値** に書かれているか。
- [ ] 観点が実はパターンや期待値にすぎない、という混同はないか。
- [ ] 「できること」「されること」のような曖昧な述語を使っていないか。使用されている場合は、具体的な仕様述語（上限制御 / 下限制御 / 復元 / 妥当性 / 反映 など）で書き直されているか。

### 2. パターンレイヤ — SHOULD

- [ ] パターンは **その観点に関係する条件だけ** を変化させているか。
- [ ] 無関係な条件（カラム名、タイブレーク設定、ラベル文言など）は **固定** され、並べ替えられていないか。
- [ ] 観点が「上限」に関するものなら、境界値（0 / 1 / 上限 − 1 / 上限 / 上限 + 1）が代表されているか。
- [ ] 無関係な次元を潰した後に、重複するパターンは残っていないか。
- [ ] パターン集合は、仕様が真であることと偽であることを区別できる **最小構成** になっているか。

### 3. 手順 / 期待値レイヤ — MUST

- [ ] 期待値は **観測可能な結果**（画面状態、保存データ、プレビュー結果）を記述しているか。
- [ ] ボタンの活性/非活性、エラーメッセージ、反映値などは、観点ではなく期待値に書かれているか。
- [ ] 手順は、その観点の観測点にたどり着くために必要な操作だけで構成されているか。全行共通の前提は「前提」として別出しされているか。
- [ ] 期待値は、プロダクションコードを読まなくても確認可能な内容になっているか。

### 4. カバレッジ — SHOULD

- [ ] 画面上の各仕様要素について、少なくとも 1 つの観点が存在するか。
  - 正しく設定できること（ハッピーパス）
  - 追加上限 / 削除下限の制御
  - 並び替え・順序付けの妥当性
  - 保存 → 再表示の復元
  - プレビュー・処理結果への反映
  - 利用可能な選択肢（カラム型など）の妥当性
- [ ] 同じ仕様の主張を別の言い回しで 2 重に書いた、冗長な観点は存在しないか。

### 5. 検出すべきアンチパターン

| 症状 | 何が問題か | 修正方針 |
| --- | --- | --- |
| 観点 = 「…を追加できること」 | 曖昧：追加 UI が存在するのか / 1 件以上追加できるのか / 上限まで追加できるのか / 上限超過で不可なのか、のいずれかが不明 | 独立した仕様の主張に分割し、それぞれを観点として書き直す |
| 観点にボタン状態の記述が混入 | 確認手段と仕様を混同している | 記述を期待値へ移し、観点は制御されるべき仕様として書き直す |
| カラム型 × 件数 × 方向 … のような全組合せを全観点で回す | 無関係次元による組合せ爆発 | 無関係な次元を固定し、観点が要求する次元だけを変化させる |
| ほぼ同一の行がラベル違いで並んでいる | 無関係次元を潰した後は重複している | マージするか削除する |
| 期待値が観点の言い換えになっている | 観測基準がない | 具体的で確認可能な結果として期待値を書き直す |

## ワークフロー

### 1) 入力の収集

- レビュー対象（markdown / シート / PR URL / 貼り付けテーブル / Notion リンクなど）を確認する。
- 対象となっている仕様（機能名、画面名）を確認する。不明な場合はレビュー前に質問する。

### 2) テストケースのパース

- 各行の 観点 / パターン / 期待値 列（または相当するもの）を特定する。
- もし 3 列分離の構造自体が存在しない場合は、**MUST** として「まず 3 列構造へ整理する」ことを提案する。

### 3) チェックリスト適用

指摘は **MUST / SHOULD / QUESTION** に分類する。

- **MUST**: 観点が操作の記述になっている／期待値が欠落または観測不能／アンチパターン #1・#2 に該当。
- **SHOULD**: 無関係なパターン／境界値の欠落／冗長な行／弱い語り口。
- **QUESTION**: 仕様の意図が不明。書き直す前に確認が必要。

### 4) 修正案の作成

- MUST 指摘ごとに、**修正行** を観点 / パターン / 期待値 テーブル形式で書く。
- 書き換えは最小限に留める。ユーザーが示唆していない新しい仕様の主張は作らない。
- ユーザーのドメイン語彙（タスク名、フィールド名）はそのまま保持する。

### 5) 報告

- サマリ: MUST / SHOULD / QUESTION の件数、構造的な問題 Top 3。
- インライン提案: **理由** を述べた上で、修正ブロックを続ける。
- 最後に、ユーザーが修正案を受け入れる前に判断すべき事項をチェックリストで示す（曖昧な仕様主張、意図的な冗長性など）。

## 出力フォーマット

各指摘は次の形を取る。

````
[MUST|SHOULD|QUESTION] <指摘内容を一行で>

理由:
<なぜ問題か、どの観点設計原則に反しているか>

修正案:
| 観点 | パターン | 期待値 |
| --- | --- | --- |
| ... | ... | ... |
````

「理由」で問題を説明し、「修正案」ブロックはユーザーがそのままテストシートへ貼り戻せる成果物とする。

## 注意事項

- ユーザーが依頼していない観点を勝手に追加しない。カバレッジの欠落を見つけた場合は **QUESTION** としてユーザーに確認し、承認を得てから新しい行を書く。
- ユーザーのテストケースがすでに良く構造化されている場合は、明示的にその旨を伝え、短く肯定的な報告を返す。問題を作り出さない。
