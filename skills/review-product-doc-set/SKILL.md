# Review Product Doc Set

## この skill の目的

この skill は、要件定義書・仕様書・画面項目定義書を **文書セット全体としてレビューする** ためのものです。

主目的は文章の上手さではありません。まず見るのは、以下です。

- 各文書が本来担うべき責務に収まっているか
- 同じ内容が複数箇所に散っていないか
- 重複が残っている場合でも整合性が取れているか
- 将来的に `画面仕様書 + Figma + 共通仕様書` に分解していく方針に沿っているか

レビュー結果は、日本語のレビューコメント案として返します。

## この skill を使う場面

- 要件定義書 / 仕様書 / 画面項目定義書のレビューを頼まれたとき
- Notion 上の文書群について、責務分離や重複を見たいとき
- Figma と Notion の二重管理を減らしたいとき
- 「この情報はどこに書くべきか」を整理したいとき

次の場面では別 skill を優先します。

- GitHub PR 上の設計書レビューなら `review-design-doc`
- 実装 PR のコードレビューなら `pr-implementation-review`
- コードの責務配置や依存方向を中心に見るなら `code-architecture-review`

## 対象スコープ

- 主対象は要件定義書、仕様書、画面項目定義書
- 必要に応じて Figma を参照する
- 共通仕様書がある場合は必ず確認する
- 文書は単体ではなく、関連文書を束ねて読む

## 基本方針

- 「正しいことが書いてあるか」より先に、「そこに書くべきことか」を見る
- 文書の責務は `WHY / WHAT / INTERACT / UI / COMMON` の観点で判定する
- 画面項目定義書をそのまま正とせず、将来の `画面仕様書 + Figma + 共通仕様書` への分解前提で評価する
- 重複は、存在そのものだけでなく、条件・文言・遷移先・上限値・例外条件の整合性も確認する
- コメントでは、問題点だけでなく「どこに寄せるべきか」を日本語で説明する

`WHY / WHAT / INTERACT / UI / COMMON` の考え方や判定例は、まず `references/review-rubric.md` を読む。今回の改善提案を根拠として詳しく確認したい場合だけ `references/documentation-improvement-proposal.md` も読む。

## 進め方

1. レビュー対象を束ねる
   - 要件定義書、仕様書、画面項目定義書、必要なら Figma と共通仕様書の対応関係を整理する
   - 文書ごとに何が正とされているか、参照先がどこかを把握する

2. 各文書の責務を確認する
   - 要件定義書は背景、課題、ユースケース、スコープに集中しているか
   - 仕様書は処理ロジック、ビジネスルール、データ制約に集中しているか
   - 画面項目定義書は UI 要素定義に閉じているか、それとも操作や条件分岐まで抱え込んでいるか
   - Figma は見た目、配置、文言、状態バリエーションの正として機能しているか
   - 共通仕様書は横断ルールの受け皿になっているか

3. 重複と整合性を確認する
   - 同じ内容が複数文書に書かれていないか
   - 重複が残っている場合、条件、文言、活性/非活性、遷移先、上限値、例外条件が一致しているか
   - 片方だけ更新されて古い説明が残っていないか
   - どちらを正として読むべきかが読み手に伝わるか

4. 将来の分解方針に照らして評価する
   - 操作起点の挙動は画面仕様書に寄せられるか
   - 見た目や文言は Figma に寄せられるか
   - 共通ルールは共通仕様書に集約できるか
   - 仕様書に残すべき処理ルールと、外へ出すべき UI 情報が混ざっていないか

5. コメント案をまとめる
   - `MUST`: 責務逸脱、明確な矛盾、更新事故につながる重複
   - `SHOULD`: 整理不足、共通化不足、将来の分解を妨げる構造
   - `QUESTION`: 意図確認が必要な箇所

## コメント案の書き方

コメントは、記号的な分類だけで終わらせず、日本語で次を説明します。

- どの箇所が問題か
- なぜその置き場所だと混乱や二重管理が起きるか
- どの文書に寄せると整理しやすいか

詳細な観点は `references/review-rubric.md`、コメントの型は `references/comment-format.md` を使う。

## 出力

返却は、原則として以下の順で行う。

1. `MUST`
2. `SHOULD`
3. `QUESTION`
4. 必要なら総評

各コメントには、少なくとも以下を含める。

- 対象箇所
- 問題の内容
- 問題になる理由
- どの文書へ整理し直すとよいか
