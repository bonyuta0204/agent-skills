# ドキュメント改善提案: コネクタ機能の要件定義書・仕様書・画面項目定義書

## 1. 背景

DEV021422（コネクタ機能の開発）を対象に、Notion上のドキュメント群とFigmaファイルを分析した結果、
ドキュメントの作成・維持工数が肥大化している構造的な問題を特定した。

本資料では現状の問題点を整理し、ドキュメント量を削減しつつ品質を担保するための改善案を提案する。

## 2. 現状分析

### 2.1 ドキュメント構成（DEV021422の実績値）

| 種別 | 件数 | 1件あたりサイズ | 備考 |
|------|------|---------------|------|
| 要件定義書 | 1 | 中 | 背景・要件・スコープ外を記載 |
| 概要 | 1 | 小（テンプレ大半が空） | セクション定義のみで中身なし |
| 機能概要 | 1 | 中 | 主要概念・フローの説明 |
| 機能詳細（仕様書） | ~25 | 大（68K文字〜） | 概要・画面遷移・設定項目・画面仕様・処理ロジック |
| 画面項目定義書 | ~14 | 巨大（200K文字〜） | UI要素を網羅的に記述 |
| 個別タスク仕様書 | ~11 | 中〜大 | 加工タスク種別ごとに1ページ |
| **合計** | **~52ページ** | | |

### 2.2 特定した構造的問題

#### 問題1: 3層での重複記述

「要件定義書 → 機能詳細 → 画面項目定義書」の3層が、抽象度を変えて同じ機能を繰り返し記述している。

![現状のドキュメント3層構造](./doc-layers-current.svg)

中間層（機能詳細）が上層・下層の両方と内容重複しており、最大の工数ドライバーとなっている。

#### 問題2: Figmaとの二重管理

画面項目定義書は1画面あたり200K+文字という膨大なサイズだが、
機能詳細中に「レイアウト・デザインの詳細はFigma参照」と記載しつつ、
Notion側にも同等レベルのUI仕様（文言・配置・状態遷移・非活性条件）を記述している。

#### 問題3: 類似パターンの個別ドキュメント化

加工タスク11種（連結・四則演算・IF文・追加・削除・型変換・書式変換・絞り込み・時刻演算・抽出・並び替え）が
それぞれ独立したページとして存在するが、ドキュメント構造はほぼ同一（設定項目・バリデーション・処理ロジック）。
差分のみが異なるにもかかわらず、共通部分を毎回フルで記述している。

#### 問題4: イベント定義の不在

「何を操作したら何が起きるか」というイベントベースの情報が体系的に整理されていない。
機能詳細の散文中に埋もれているため、テストケース作成者が全イベントパスを網羅しづらい。
結果として「このテストどうやったらいいですか」という問い合わせが発生している。

## 3. 改善提案: 新しいドキュメント構成

### 3.1 全体像

現状の「要件定義書 → 機能詳細 → 画面項目定義書」を、責務が明確に分離された4層 + 共通仕様書に再構成する。

![改善後のドキュメント構成](./doc-layers-proposed.svg)

| 層 | ドキュメント | 責務 | 主な読者 | 単位 |
|---|------------|------|---------|------|
| **WHY** | 要件定義書 | なぜ作るのか、何を実現するのか | PdM・企画・全員 | 開発対象に1つ |
| **WHAT** | 仕様書 | 処理ロジック・ビジネスルール・データ制約 | 開発者 | 機能ごとに数ページ |
| **INTERACT** | 画面仕様書 | 操作したら何が起きるか（イベント→アクション→遷移） | QA・テスト設計者・開発者 | 画面ごとにテーブル1つ |
| **UI** | Figma | 見た目・レイアウト・文言・状態バリエーション | デザイナー・開発者 | 画面ごと |
| **COMMON** | 共通仕様書 | プロダクト横断の入力制御・バリデーション・表示ルール | 全員 | プロダクトに1つ |

### 3.2 各層の詳細

#### 要件定義書（WHY）

**現状の要件定義書 + 概要 + 機能概要を統合**して1ページにまとめる。

記載内容:
- 背景・課題
- ユースケース
- 方針（スコープ内/外）
- 主要概念の定義（データボード・ジョブ・カード等）
- 検討経緯（複数案を比較した場合のみ）

記載しない:
- 処理ロジックの詳細 → 仕様書へ
- 画面の操作フロー → 画面仕様書へ
- UIの見た目 → Figmaへ

#### 仕様書（WHAT）

**現状の機能詳細からUI記述を排除**し、処理ロジックとビジネスルールに特化。
類似パターン（加工タスク11種等）はテーブル形式で集約する。

記載内容:
- 処理ロジック（プレビュー生成フロー、データファイル化の実行順序等）
- ビジネスルール（1ジョブあたり最大50タスク、プレビューは先頭1000レコード等）
- バリデーションルール（入力制約、型制約）
- データ制約・パフォーマンス要件
- API仕様（リクエスト/レスポンス形式）

記載しない:
- 画面レイアウト（ヘッダ・ボディ・フッタの構成等） → Figmaへ
- ボタンの文言 → Figmaへ
- 操作時の画面遷移 → 画面仕様書へ

**類似仕様のテーブル集約:**

現状11ページの加工タスク仕様書を1ページに集約する。

| タスク名 | 入力パラメータ | バリデーション | 出力 | 固有の制約 |
|---------|--------------|-------------|-----|----------|
| 連結 | カラム2つ以上, 区切り文字 | カラムが2つ以上選択されていること | 連結済みカラム | なし |
| 四則演算 | カラム2つ, 演算子 | 数値型カラムであること | 計算結果カラム | ゼロ除算エラー |
| ... | ... | ... | ... | ... |

#### 画面仕様書（INTERACT）

**新設**。現状の画面項目定義書（200K+文字/画面）を、イベントカタログ形式のテーブルに置き換える。
画面ごとに「何を操作したら、どの条件で、何が起き、どこに遷移するか」を網羅する。

記載内容:
- イベント定義テーブル（トリガー → 条件 → アクション → 遷移先）
- 対応するFigma画面へのリンク

記載しない:
- UI要素の見た目・文言・配置 → Figmaへ
- 処理ロジックの詳細 → 仕様書へ

**具体例: 連結タスク設定画面**

| # | トリガー | 条件 | アクション | 遷移先 |
|---|---------|------|----------|-------|
| 1 | カラム1セレクト変更 | - | プレビュー再取得 | - |
| 2 | カラム2セレクト変更 | - | プレビュー再取得 | - |
| 3 | 適用ボタン押下 | カラム2つ以上選択 & カラム名入力済 | タスクをリストに追加 | タスク一覧（閲覧モード） |
| 4 | 適用ボタン押下 | 条件未達 | 非活性（押下不可） | - |
| 5 | キャンセルボタン押下 | - | 設定内容を破棄 | タスク種別選択画面 |
| 6 | タスクアイテム選択 | - | タスク詳細を閲覧モードで表示 | タスク詳細設定画面（閲覧） |
| 7 | 新規タスク追加ボタン押下 | 設定中タスクなし | タスク種別選択を開く | タスク種別選択画面 |
| 8 | 新規タスク追加ボタン押下 | 設定中タスクあり | 非表示（ボタン自体がない） | - |
| 9 | 削除ボタン押下 | 末尾タスクの閲覧時のみ表示 | 対象タスクを削除 | 削除後末尾タスクの閲覧 |
| 10 | セル選択（プレビュー） | - | セルプレビューに全文表示 | - |
| 11 | カラム検索バーでEnter/フォーカスアウト | - | カラムをフィルタリング | - |

この形式の利点:
- **テストケース作成**: 行を上から舐めるだけで全イベントパスを網羅できる
- **QA**: 「このボタン押したらどうなるの？」が自己解決できる
- **複数導線の可視化**: 同一トリガーが条件違いで複数行になるので分岐が一目瞭然
- **記載量**: 1画面あたりテーブル10〜30行（現状の200K+文字 → 数千文字）

#### Figma（UI）

画面のビジュアル定義のSingle Source of Truth。

記載内容:
- レイアウト・配置
- 文言・ラベル
- 状態バリエーション（初期表示・入力中・エラー・非活性・エンプティステート）
- Annotation（非活性時・エラー時の見た目の補足）

記載しない:
- 処理ロジック → 仕様書へ
- イベントフロー → 画面仕様書へ

#### 共通仕様書（COMMON）

**新設**。プロダクト横断で適用される入力制御・バリデーション・表示ルールを1箇所に集約する。
開発対象によらずプロダクト全体で1つだけ存在し、各機能の仕様書・画面仕様書から参照される。

現状、これらのルールは画面項目定義書の各ページに同一の「ガイド」としてコピペされているが、
更新時に全ページを修正する必要があり、実際には陳腐化している。

記載内容:

| カテゴリ | 例 |
|---------|---|
| **入力制御** | 整数フィールドへの小数入力時の挙動、最大文字数超過時の挙動、半角/全角の自動変換ルール |
| **バリデーション優先順位** | 非表示 > 権限非活性 > その他非活性 |
| **バリデーション時の表示制御** | どのような場合に非表示にするか、どのような場合に非活性にするかの基準 |
| **エラー表示パターン** | トースト/ツールチップ/インラインの使い分け基準 |
| **権限制御** | 権限不足時のツールチップ文言ルール（アプリ権限 > フォルダ権限 > 個別権限） |
| **連打制御** | どの操作に連打制御が必要か（データ更新系は要、閲覧系は否） |
| **検索仕様** | 部分一致/前方一致の基準、検索実行タイミング（フォーカスアウト or リアルタイム） |
| **NULL表示** | NULLの場合は「NULL」テキストを薄灰色で表示 |

共通仕様書があることで、各画面仕様書のイベントテーブルでは個別の挙動を毎回記述せず、
共通仕様への参照で済ませることができる。

```
毎回書く（冗長）:
| 3 | 金額フィールドに小数入力 | - | 小数点以下切り捨て、エラーツールチップ表示 | - |

共通仕様を参照（簡潔）:
| 3 | 金額入力 | - | 共通仕様: 整数フィールド準拠 | - |
```

### 3.3 各層の境界判定ルール

「この情報はどこに書くべきか？」を迷わないための判定フロー:

1. **全機能で共通のルールか？** → Yes: 共通仕様書
2. **なぜこの機能が必要か？** → 要件定義書
3. **データや処理はどう動くか？** → 仕様書
4. **ユーザーが操作したら何が起きるか？** → 画面仕様書
5. **画面はどう見えるか？** → Figma

境界が曖昧になりやすいケースの判定例:

| 情報 | 判定 | 理由 |
|------|-----|------|
| 「整数フィールドに小数が入力されたら？」 | **共通仕様書** | 全機能共通の入力制御ルール |
| 「バリデーション時に非表示 or 非活性のどちらにするか」 | **共通仕様書**（基準）+ **画面仕様書**（個別適用） | 基準は共通、どの要素に適用するかは画面ごと |
| 「ボタンが非活性になる」 | **画面仕様書**（条件）+ **Figma**（見た目） | 条件はINTERACT、見た目はUI |
| 「プレビューは先頭1000レコード」 | **仕様書** | データ制約であり操作起点ではない |
| 「適用ボタンを押すとタスクが追加される」 | **画面仕様書** | イベント→アクションの定義 |
| 「タスク追加時にリスト末尾にオブジェクトを生成」 | **仕様書** | 内部処理ロジック |
| 「エラー時にトースト表示」 | **画面仕様書**（トリガー）+ **Figma**（見た目） | |
| 「ボタンの文言は『適用』」 | **Figma** | UI表現 |
| 「連打制御が必要か」 | **共通仕様書**（基準）+ **画面仕様書**（個別適用） | |
| 「権限不足時のツールチップ文言」 | **共通仕様書** | プロダクト横断の文言ルール |

## 4. 現行ドキュメントからの移行マッピング

| 現行ドキュメント | 移行先 | 対応 |
|----------------|-------|------|
| 要件定義書 | 要件定義書 | ほぼそのまま |
| 概要（`2_概要`） | 要件定義書に統合 | 空テンプレのため実質廃止 |
| 機能概要 | 要件定義書に統合 | 主要概念の定義として取り込み |
| 機能詳細 > 概要 | 不要（要件定義書でカバー） | 廃止 |
| 機能詳細 > 画面遷移 | 画面仕様書 | イベントテーブルの遷移先カラムへ |
| 機能詳細 > 設定項目 | 仕様書（ルール部分）+ Figma（UI部分） | 分離 |
| 機能詳細 > 画面仕様 | 画面仕様書（イベント部分）+ Figma（レイアウト部分） | 分離 |
| 機能詳細 > 処理ロジック | 仕様書 | そのまま移行 |
| 画面項目定義書 | Figma + 画面仕様書 + 共通仕様書 | 見た目→Figma、操作→画面仕様書、共通ルール→共通仕様書、それ以外は廃止 |
| 画面項目定義書 > ガイド（全ページにコピペ） | 共通仕様書 | バリデーション優先順位・権限制御ルール等を集約 |
| 個別タスク仕様書（11ページ） | 仕様書（テーブル集約1ページ） | 共通部分を抽出、差分をテーブル化 |

## 5. Figma現状分析と課題

対象Figmaファイル: `加工の一連の流れをkpiee化する`（fileKey: R0ZZujRNMT1gdUalgz5Y4Z）

### 5.1 確認した画面

- **連結タスク設定画面（kpiee版）**: 左にタスクリスト、中央にタスク設定フォーム、右にデータプレビューの3カラム構成
- **データボードキャンバス（kpiee版）**: ジョブをノード&エッジで接続するフロー画面
- **データファイル選択・ジョブ追加（b→dash版）**: サイドパネルでデータファイルを選択し処理方法を設定
- **更新設定画面**: 定期更新の有無・頻度・時刻を設定するサイドパネル

### 5.2 Figma側の課題

| 問題 | 内容 | 改善案 |
|------|------|-------|
| **b→dash/kpiee混在** | 同一ファイルに旧UI（青ヘッダ）と新UI（ピンクヘッダ）が混在 | kpiee版を正とするページを明確化。b→dash版は別ページに分離 |
| **フレーム名が非体系的** | トップレベルフレームの大半が「データボード作成」という同一名。個人作業フレームも混在 | 命名規則の導入: `[アプリ名]_[画面名]_[状態]` |
| **コンポーネント化不足** | テーブルプレビューが罫線の手動配置。設定ブロックが都度作成 | 共通コンポーネントとして抽出 |
| **Annotationなし** | 非活性条件・バリデーション等の仕様注記がFigma上に一切ない | Dev ModeのAnnotations機能で補足情報を記載 |
| **proto URL共有** | 実装者に必要なのはDev Mode（`/design/`）なのにプロトタイプURL（`/proto/`）で共有 | `/design/` 形式に統一 |

### 5.3 Figmaに記載すべきAnnotationの範囲

新しいドキュメント構成では、Figma Annotationの役割は**画面仕様書の補足**に限定される。

Annotationに書く:
- 非活性時の見た目（どのスタイルになるか）
- エラー表示の見た目（トースト/ツールチップ/インライン等）
- エンプティステートの見た目

Annotationに書かない（画面仕様書に書く）:
- 非活性の条件（なぜ非活性になるか）
- エラーの発生条件（何をしたらエラーになるか）
- 遷移先（どこに飛ぶか）

この分離により、Figma Annotationの記載量は最小限に抑えつつ、
画面仕様書のイベントテーブルが操作の全体像を担保する。

## 6. 期待効果

### ページ数の変化

| | 現状 | 改善後 |
|---|---|---|
| 要件定義書 | 1 | 1（概要・機能概要を統合） |
| 仕様書 | 25（機能詳細）+ 11（タスク別） = 36 | 数ページ（処理ロジック特化）+ 1（タスクテーブル集約） |
| 画面仕様書 | 0（存在しない） | 画面数分（10〜15程度のテーブル） |
| 画面項目定義書 | 14 | 0（Figma + 画面仕様書 + 共通仕様書に分解） |
| 共通仕様書 | 0（各ページにコピペで散在） | 1（プロダクト横断で共有） |
| **合計** | **~52ページ** | **~15〜20ページ + 共通仕様書1ページ** |

### 記載量の変化

| ドキュメント | 現状 | 改善後 |
|------------|------|-------|
| 機能詳細 1ページ | 68K文字〜 | 数千文字（処理ロジックのみ） |
| 画面項目定義書 1画面 | 200K文字〜 | 0（Figmaに移行） |
| 画面仕様書 1画面 | 存在しない | テーブル10〜30行（数千文字） |
| タスク仕様 | 11ページ分 | テーブル1ページ |

### 定性的効果

- **テストケース作成**: 画面仕様書のイベントテーブルから機械的にテストケースを導出可能
- **「このテストどうやるの？」の削減**: イベント→アクション→遷移先が一覧化されている
- **複数導線の見落とし防止**: 条件分岐が行として可視化される
- **Figmaとの二重管理解消**: UI情報はFigma、操作情報は画面仕様書と明確に分離

## 7. 導入ステップ

1. **共通仕様書の作成**: 現在の画面項目定義書から「ガイド」部分（バリデーション優先順位・権限制御・連打制御等）を抽出し、1ページに集約
2. **テンプレート作成**: 要件定義書・仕様書・画面仕様書のNotionテンプレートを作成
3. **Figma運用ルールの策定**: デザイナーと合意し、フレーム命名規則・Annotation基準を標準化
4. **パイロット適用**: 次の開発対象で新フォーマットを試行し、フィードバックを収集
5. **既存ドキュメントの段階的移行**: 改修が入るタイミングで順次新フォーマットに移行（一括移行は不要）
